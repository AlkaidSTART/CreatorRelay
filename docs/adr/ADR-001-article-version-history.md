# ADR-001：文章版本历史采用 Git 快照仓库

- **状态：** Accepted（用户于 2026-11-25 确认）
- **决策范围：** M2 本地工作区；M5 Studio 复用
- **上下文：** PRD §16.2 将 Git 与文件快照列为待决方案。文章文件必须始终是正文权威来源，历史恢复不能丢失被替换版本，也不能要求用户另行安装 Git。

## 决策

1. Rust Core 使用 `git2`（libgit2）在应用数据目录创建 bare repository；每个规范化后的工作区路径对应独立仓库。工作区本身不创建 `.git`。
2. 仓库树只包含 CreatorRelay 管理的 `articles/<id>/article.md` 主稿。素材、模板、导出物及工作区内其他文件不进入版本仓库。
3. 新建和导入文章创建初始版本；自动保存只写 Markdown 与 SQLite 索引，不自动创建版本。用户可在版本历史面板显式创建带说明的版本。
4. 版本记录提供基于统一 diff 的文件差异查看。恢复前将磁盘当前稿纳入历史，恢复结果以新的提交成为当前版本；旧提交保持不变。
5. 初次访问文章历史时，若旧 SQLite `revisions` 表存在，则按创建时间迁移其快照；迁移不改写 Markdown 文件。
6. 保存使用加载时的内容哈希做乐观冲突校验。检测到外部修改时先将磁盘版本保存在 Git 历史中，再由用户选择重载或保留应用草稿。

## 备选方案

- **仅 SQLite 文件快照：** 已有原型实现简单，但快照与业务数据库生命周期绑定，差异与版本语义需自行实现。
- **工作区内 Git 仓库：** 容易随工作区迁移，但会把实现细节暴露给用户，也可能与用户现有仓库冲突。
- **应用内 bare Git：** 采用此方案；无需系统 Git，版本对象与用户工作区隔离，具备成熟 diff/提交对象模型。代价是应用数据目录需纳入备份；按工作区路径寻址意味着移动/改名工作区后的历史迁移仍需专门设计。

## 后果与限制

- Git 历史不是工作区可移植文件的一部分；换机器、清理应用数据或移动工作区前，当前版本仍在 Markdown 文件中，但历史不会自动随文件迁移。
- 当前实现不冻结自动备份频率、加密、保留策略或 Git 历史 GC；这些仍按 PRD §16.3 后续决策。
- 外部编辑器不参与应用锁。哈希检查能识别已发生的修改，但文件系统没有通用 compare-and-swap 写接口，极窄的检查到原子替换窗口仍有并发竞争风险。
