# CreatorRelay 阶段功能文档

每个阶段文档均包含“阶段任务总结”。该总结只记录当前实施进度、阻塞和下一步，并链接到独立的验证记录，不是验收报告；验证命令、AC 快照和手工证据统一放在 [`progress/verification/`](./verification/README.md)，只有阶段文档中的全部 AC 验证通过后，才可创建对应的 `M*-acceptance.md`。

## 推荐实施顺序与阶段门

按 M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8 推进。M2 与 M3 在 M1 之后可以并行开发，但进入 M4 前必须统一账号、凭据和会话接口。

- **本地创作可用：** M1、M2、M5 验收通过后，用户可离线创建、编辑和检索视频、图文、图文文章及纯文章。
- **MVP 核心闭环：** M1–M7 的必要能力完成，并满足 PRD 14.1；至少两个平台适配器须按实际开放能力完成验证，且验证范围至少覆盖一种媒体优先形态和一种文章形态。MVP 验收不要求所有平台都支持全部内容形态或自动发布。
- **扩展能力：** M8 逐个平台按接入准入与兼容性标准扩展。完整第三方插件市场、团队协作、云端同步、专业视频剪辑和复杂多 Agent 编排不属于 MVP。

## 全阶段通用验收约束

1. 功能验收以各阶段文档中的 AC 编号为准；未满足的项目不得标记为通过。
2. 每个里程碑均需提供适用的单元测试、集成测试、数据库迁移测试、异常恢复测试和开发文档（PRD §15）。
3. 内容形态、元数据和媒体顺序以内容包清单为权威来源；图文文章和纯文章正文以 Markdown 为权威来源。视频和图文不要求 Markdown 正文，SQLite 仅保存索引和业务元数据，不可反向覆盖用户文件。
4. 密码、Cookie、Token、API Key 等敏感值不得明文落入 SQLite 或日志；凭据通过统一凭据服务访问。
5. 平台能力必须以实际验证结果声明。平台政策、授权或接口不允许自动化时，必须提供人工操作路径，不得绕过平台限制。
6. 发布、删除及其他外部副作用在执行前必须明确展示目标并获得用户确认；超时但结果不确定时不得盲目重试。
7. 阶段状态、实际完成日期和验收证据由项目实施过程维护；本目录本身不预设任何实现进度。

## 待冻结事项

进入相关阶段实施前，应将 PRD §16 的建议项转化为 ADR/TDD 决策：插件运行时与隔离边界（M4）、内容包与 Markdown 版本策略（M2/M5）、大型视频的存储/备份策略（M1/M2）及不同操作系统上的浏览器会话实现（M3）。在决策完成前，阶段需求不把建议写成既成事实。
